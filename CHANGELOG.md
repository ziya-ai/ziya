## [0.8.10.0] - 2026-10-14

### Added
- **The `git` tool can amend the top commit and force-push, and asks you every time.** Until now a stacked-change hand-off ended with "my git tool can't --amend or force-push" and two commands for you to type. `commit` now takes `amend: true`: it replaces HEAD with HEAD plus what's staged (or exactly `paths`), and keeps HEAD's message if none is given. The approval names the replaced commit and warns when it's already on a remote branch. `push` now takes `force: true`, which is `--force-with-lease=refs/heads/<b>:<sha>` on the remote-tracking sha shown in the approval and never a bare `--force`. The approval lists every remote commit that would be dropped, a remote that moved since your last fetch is refused by git with a hint to `fetch`, and forcing the remote's default branch is refused outright. Both run under their own consent ops, `commit_amend` and `push_force`, declared in the new `consent_human_only_ops`. For those ops the gate always asks: a `permissions.json` `always`, an autonomous project, or a conversation or session grant doesn't skip the prompt, and the panel offers "once" only. Approving `commit` or `push` therefore never approves a history rewrite. `git_ops.truthy` reads the flag the same way for dispatch and for the consent op, so `amend: "false"` is a plain commit in both places (plain `bool("false")` would ask about a commit and then amend). (`app/utils/git_ops.py`, `app/utils/consent_gate.py`, `app/mcp/tools/git_tool.py`, `app/utils/git_grant_hazards.py`, `design/git-tool.md`, `Docs/Capabilities.md`; tests `tests/test_git_ops_amend_force.py` (new), `tests/test_git_ops_fixup.py`)
- **The Conversation Info dialog's Cost row lists the spend per model.** Each ledger row already records the model that answered that call and is priced at that model's rate, so a conversation that switched models mid-way was summed correctly — but only the total was shown, beside no model at all, which read as "priced at the current model". The row now shows one line per model (`global.anthropic.claude-opus-5-5 · $48.07 · 288 calls`, …) under the total. The conversation rollup is grouped by model instead of status; the estimate/actual split the row needs comes from `totals`, so nothing was lost. (`frontend/src/api/usageApi.ts` — `fetchConversationCost`, new `modelGroupLabel`; `frontend/src/components/ConversationInfoModal.tsx`; test `frontend/src/api/__tests__/usageApi.test.ts`)
- **Task cards can be exported to a file and imported into another deck.** The deck has **Export** on each card's `⋯` menu and in the editor toolbar, **Export all** and **Import** beside New/Refresh; `GET /task-cards/export[?ids=…]`, `GET /task-cards/{id}/export` and `POST /task-cards/import` back them. The file (`<name>.ziya-task-cards.json`) is the card's *definition* only: `id`, run history, `version`, `draft` and `source` are stripped, as are every default-valued and null field, so a 4-block card is a few hundred bytes of readable tree rather than 8 KB with ~190 `null`s and a task block claiming `schedule_enabled: true`. An `about` list in the envelope explains the block vocabulary, `{{sibling("ID")}}` and what `scope` means, for a reader (or another tasking agent) with no Ziya knowledge. Import remints every block id and rewrites `sibling()` references to follow — the same reason Duplicate remints: approvals key on block id, so a signature from another machine must not authorize anything here, and an imported escalating card shows **Unsigned** until signed in this deck. An import is all-or-nothing; a name collision (a `call` by name resolves the first match) and launch-validator findings are reported as warnings, not refusals. A bare card object or a list of cards imports too. Also carries the card's `requires` block through create, which `TaskCardCreate` previously dropped. (`app/storage/task_cards.py`, `app/api/task_cards.py`, `app/models/task_card.py`, `frontend/src/services/taskCardApi.ts`, `frontend/src/components/TaskCard/TaskCardsLibrary.tsx`; tests `tests/test_task_card_export_import.py` (new, 32))
- **`git` tool `fixup` op: fix a commit in the middle of the stack** (`app/utils/git_ops.py` (`plan_fixup`, `op_fixup`; `_commit_files` / `_record_commit` factored out of `commit`), `app/mcp/tools/git_tool.py` (`target` argument), `frontend/src/components/ConsentPreflight.tsx` (summary sentence); tests `tests/test_git_ops_fixup.py` (new, 15), `tests/test_git_tool_schema_parity.py` (+1), `__tests__/ConsentPreflight.test.tsx` (+1); `Docs/Capabilities.md`, `design/git-tool.md`). The tool could only commit on top of HEAD, so a fix that belonged in an earlier commit had no route through it. `git(op="fixup", target=<commit>)` commits the staged changes (or exactly `paths`) as `fixup! <target subject>` and returns `fold_in`, the `git rebase -i --autosquash` command that folds it into the target. The tool never runs the rebase, so it still never rewrites history. The approval shows the target, the files and the commits after it, and warns when the target is already on a remote branch or a merge commit is in the way. A target that isn't an ancestor of HEAD is refused.

- **A container's child can be marked `required: false`** (`app/models/task_card.py` (`Block.required`), `app/agents/block_executor.py` (`_execute_parallel`, `_execute_sequence`), `app/data/built_in_skills.py` (`task_cards` grammar), `frontend/src/types/task_card.ts`; tests `tests/test_block_required_false.py` (new, 9; the positive cases fail on the old executor, which counted every child)). A Parallel reported failed whenever any child failed, and under `Group(stop)` that halted the run, so a fan-out of `{1A baseline, 1B known-issues}` had no way to say that 1A must pass and 1B may not. An optional child's failure now neither trips an enclosing `on_failure: "stop"`, nor makes a Parallel report failed, nor — as the last child of a sequence — fails the sequence's own artifact; a child that raises is treated the same way. It is recorded, not hidden: the container's `decisions` carry "optional child <name> failed … (required=false)" with the child's signature, the child's own stage evidence still reads failed, and the next sibling still receives the failed artifact as `{{previous_sibling}}`. Default `true`, so every existing card is unchanged. Also corrects the grammar text added earlier in this release, which said `on_failure` on a Parallel governs sibling cancellation: `_execute_parallel` does not read it at all.
- **A satisfied output contract outranks a `partial` self-assessment** (`app/agents/task_executor.py` (verdict/contract reconciliation after the contract check), `app/utils/completion_check.py` (`is_failure` docstring), `app/data/built_in_skills.py` (`task_cards` grammar); tests `tests/test_output_contract_overrides_partial.py` (new, 6; the positive case fails on the old executor, whose contract check could only add failure and never clear it)). A task that emitted every `required` entry of its `output_contract`, each validating against its pinned schema, and then closed with `objective_met="partial"` was recorded failed — and under `Group(stop)` halted the run — on the strength of its own self-report. The contract tests the thing the verdict exists to catch ("did this task abandon its goal mid-run?") directly, so when a required contract is fully satisfied the task is now recorded ok and the verdict kept as a warning: in `decisions` with the model's rationale, and as `self_assessment` on the artifact and the `task_finished` event. Unchanged: a task with no contract or an all-optional contract (the verdict is the only evidence), a `false` verdict (a model that says false with every output present is contradicting itself), an unmet contract, and the empty/truncated-stream failures, which stand even with outputs present.
- **A Schedule says what a due slot does while a run of its card is still live** (`app/models/task_card.py` (`Block.schedule_concurrency`), `app/agents/task_scheduler.py` (`_tick_card`, `_concurrency_gate`, `_live_runs_for_card`; the fire pass is extracted from the loop body so the decision is testable), `app/data/built_in_skills.py` (`task_cards` grammar), `frontend/src/types/task_card.ts`, `frontend/src/components/TaskCard/ScheduleBlockEditor.tsx` ("if still running" selector); tests `tests/test_task_scheduler.py` (7 added — the default-skip case fails on the old scheduler, which fired). The scheduler had no notion of overlap: a slot fired while a previous fire, or a hand-launched run of the same card, was still running the same workspace, and a laptop waking at 09:00 fired the missed 03:00 catch-up slot on top of a run started by hand at 08:00. `schedule_concurrency` is `skip` (default: the slot is dropped, `next_fire_at` advances, and the skip is recorded in the card's schedule-state as `skips[]` / `skips_so_far` / `last_skip_at` with the live run's id, so GET …/schedule-state shows "skipped: run <id> still live" instead of silence), `queue` (the slot is held with `deferred_since` and fires on the first tick after the live run ends, bypassing the catch-up gate since a deferral is a decision to run late, not a missed slot), or `parallel` (the previous behaviour).
