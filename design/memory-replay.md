# Longitudinal memory replay

## Why

Every memory heuristic added on 2026-09-25..27 (provenance share 20%,
collection evidence floor 25%, rebalance margin 2x, restore containment 0.6,
7 domain sessions, cleanup removal cap 25%) was checked against one snapshot
of one store.  The existing evaluation stack (`scripts/memory_quality_score.py`
golden set, `memory_eval_ab.py`, the search-only A/B harness,
`run_memory_lifecycle_simulation.py`) scores **per-conversation extraction**.
None of the defects found in this period are visible at that level: they only
appear over weeks, across interleaved domains, in an accumulating store
(cleanup false positives compounding over 217 organize runs; the gravity-well
root; the global activity clock aging one project's proposals on another's days).

The replay re-runs the whole memory system over the real conversation history
in timestamp order, into a sandbox store, so a change is judged by what the
store becomes.

## Corpus (measured 2026-09-27)

`scripts/memory_replay/timeline.py`: 1,816 chat records, 25,416 messages, all
with ms timestamps.  12,144 extraction events from 1,210 chats, 2025-12-02 to
2026-09-27.  516 of 2,007 active hours touched two or more projects; 3,735
project switches between consecutive events.  ~26% of events are from a second project family,
~62% Ziya.

## Event model

- **extract** at each assistant reply's timestamp, over the history before it
  (what `app/server.py` passes).  Fork prefixes are skipped; delegate chats
  and shells excluded; muted/system/empty rows dropped.
- **lifecycle** every 30 simulated minutes, **organize** (cleanup + bootstrap +
  consolidate + ...) on the `memory_organize` job's 6 h cadence and gate,
  **maintenance/repair** after each save as production does.  Scheduled
  events are generated by the engine from the simulated clock, not stored.

## Engine (built 2026-09-27: `scripts/memory_replay/`)

| module | role |
|---|---|
| `arms.py` | `export-baseline` (git archive 5e0e1562 app scripts, unpacked by Python), `freeze-current` (one-time copy of `app/`), `freeze-harness`, `hash` |
| `sandbox.py` | caller-scoped `get_ziya_home` redirect for memory modules + singleton swaps + audit writers replaced by name counters + `sys.addaudithook` write guard over the real `~/.ziya`; sha256 of every file under `~/.ziya/memory` checked on exit |
| `simclock.py` | replaces the `time` / `datetime` / `uuid` module references *inside memory modules only* with shims that follow the event clock; `uuid4` is a seeded counter so ids are reproducible |
| `llmcache.py` | record/strict cache of `call_service_model` + embedding provider; one ALE-encrypted file per key, published with `link(2)` (EEXIST semantics of `O_EXCL`): first writer wins, losers discard their response |
| `events.py` | timeline extract events + audit `memory_propose`/`memory_save` (truncated contents restored from the real store when unambiguous) + `Scheduler` |
| `attribution.py` | diff of every `_save_memories` write -> `transitions.jsonl` (ids, statuses, cause from the call stack); lost-memory and proposal texts -> `texts.enc` (encrypted) |
| `engine.py` | the run loop, checkpoints (every 200 events, at pause, at end), resume with log truncation to the checkpoint |
| `metrics.py` | `scorecard.json` + `weekly.jsonl` |
| `compare.py` | plaintext-canonical comparison of final stores |

Per extract event the engine does what production does after a streamed
reply: builds the memory prompt section (so `record_load` / labile windows
happen), `apply_feedback(chat, recorded reply)`, then
`run_post_conversation_extraction(history, chat, project_name, project_path)`,
then drains every task the memory code spawned (post-save maintenance,
periodic cleanup, auto-organize) before the next event.  Production runs
feedback and extraction as concurrent fire-and-forget tasks; the replay
serialises them (feedback first), which is the order production schedules.

**Scheduled jobs and idle gaps.**  The engine calls the ARM's own
`app.agents.system_jobs.tick_system_jobs(now_ms=T)`, so each arm's intervals
and gates apply.  The real scheduler ticks only while a server is up.  The
replay treats the server as up for 1 h (`--idle-gap-min`) after each event:
a job due inside that window ticks at its due time; a job whose interval
elapsed during a longer idle gap ticks **once, at the first event after the
gap** (before that event), however many intervals elapsed.

**Determinism.**  `PYTHONHASHSEED=0` (the CLI re-execs), seeded uuid4,
simulated time, cached model/embedding responses.  Two strict replays of a
recorded run produce identical decrypted stores (checked by the tests and by
the smoke).  Resume after a stop yields the same final state as an
uninterrupted run (tested).

## Engine (original plan)

- **Sandbox**: all store seams patched to a per-arm directory, as
  `memory_quality_score._sandbox_patches` does, plus `memory_clock._default_path`
  and the activity counter.  `~/.ziya/memory` hashes checked before/after.
- **Simulated time**: `time.time` / `time.strftime` in the memory modules follow
  the event clock, so `created`, `archived_at`, clock stamps and the dormant
  backstop see replay time, not wall time.
- **Record/replay cache** for `call_service_model` and the embedding provider,
  keyed by sha256 of (category or model, system prompt, user message,
  max_tokens, temperature).  Arms that differ only downstream of the model
  replay for free and deterministically.  Arms that change what is sent miss
  the cache and call live; their noise floor comes from an A/A run.
- **Arms** are source trees: the live tree, and `HEAD` exported read-only
  (`git archive`) as the pre-session baseline.  Each arm runs in its own
  process with its own tree first on `sys.path`.
- **Checkpoints**: store snapshot + event cursor every N events so a long run
  resumes.

## Metrics

Judge-free, per arm, sampled over time:

| metric | definition | catches |
|---|---|---|
| retention | of memories ever active, share still active at end; by layer and domain; each loss attributed (cleanup, merge, decay, dormant, repair) | cleanup attrition |
| relearn rate | proposals whose text matches (>=0.6 containment) a memory the store once held and lost | harmful forgetting |
| domain fairness | domain share of active store vs share of events | a minority project shrinking on Ziya weeks |
| structure | largest-node share, max root tags, per-node project mix, orphan rate, depth | gravity wells |
| promotion latency | proposal -> active, in events and in domain sessions | clock tuning |

Plus the existing golden-set scorer for extraction quality.  Differences are
reported as paired deltas against the A/A band.

## Home seams (all redirected or neutralised by `sandbox.py`)

`MemoryStorage`/`ProposalsStore`/`EmbeddingCache` constructors and
singletons; `extractor._next_activity_count` and
`lifecycle.current_activity_count` (activity_counter.json);
`feedback._stats_file`; `maintenance._get_cleanup_state_file`;
`organize_history._history_file`; `memory_clock._path`/`_default_path`;
`system_jobs._state_path` (module-level `get_ziya_home` import);
`tool_audit_log` (`_LOG_DIR`, `log_security_event`, `log_tool_execution`,
reached from prompt.py NF-010, storage save NF-010 and the encoding
scanner); `eval.py`'s `Path.home()` paths are eval-only and not reached.
Anything else is refused by the audit-hook write guard.  The before/after
hash of `~/.ziya/memory` also sees the user's LIVE Ziya server, which shares
the home: a change is attributed to the replay (critical) when the guard
refused a write or a replay-minted memory id (seeded uuid4) appears in the
real store, otherwise to an external writer -- reported loudly, logged to
`external_changes.jsonl`, and the chunk exits 3 after its checkpoint.

## Smoke (2026-09-27, `current` arm, 2026-09-20..27, empty start)

694 events (601 extract, 87 propose, 6 save) + 218 ticks (210 lifecycle,
20 organize runs).  Record run: 6 chunks, 5,173 live model calls, 5,301
live embeddings, 0 errors cached.  Strict replay: 0 misses, 13 min, final
store identical to the record run file by file (decrypted), plus identical
transitions.jsonl, events.jsonl and weekly.jsonl -- although the record run
was resumed five times, once across a harness edit.

## Known limits

- Assistant replies were generated with the historical store, so retrieval
  "used" signals reflect history, not the arm's store (smoke: 0 of 133
  loaded memories scored as used).
- Only `memory_propose`/`memory_save` tool calls are replayed.  The model's
  `memory_search`/`memory_context`/`memory_expand` calls (which also
  `record_load`) and `memory_retract_proposal` are not, so once a mind-map
  exists (prompt shows handles, not facts) feedback has nothing loaded.
- The audit log truncates tool args at 500 chars; truncated contents are
  restored from the real store only when exactly one record from the same
  conversation matches (smoke: 58 truncated, 45 restored, 13 replayed cut).
- Feedback and extraction run sequentially and every spawned task is drained
  before the next event; production runs them as concurrent background
  tasks that can overlap the next turn.
- Server uptime is modelled as 1 h after each event (`--idle-gap-min`).
- A prompt repeated within a run gets the one cached response (smoke record:
  1,009 in-run hits); production would sample again at temperature > 0.
- Edited/truncated messages replay in final form; the system prompt part of
  the request is not reconstructed, and production's LangChain `system`
  message is absent from the extraction history.
- Window runs (like the smoke) start from an empty store, not the
  historical store at the window start.
- `app.api.memory` is stubbed (`_organize_task_status.running = False`,
  the value it has whenever no UI-triggered organize is running) because the
  real module imports the whole API package.
